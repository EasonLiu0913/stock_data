# 股票預測事後覆盤機制

這份文件定義「事前預測」完成後，如何在下一交易日實際行情資料到位時，產生事後覆盤、準確與不準清單、以及後續因子歸零測試。目標是讓預測系統能逐步驗證哪些判斷要素有效，而不是只是不斷疊加更多因子。

範例：目前已有 `data_predictions/20260727/summary.json`，這批資料代表用 `2026-07-24` 的基準資料預測 `2026-07-27`。等爬蟲取得 `2026-07-27` 真實行情後，就可以對這批預測做覆盤。

## 核心目標

- 比對每檔股票的事前預測與下一交易日實際走勢。
- 在覆盤檔內保存完整事前預測快照、來源路徑與 SHA-256；不得用事後資料覆寫預測欄位。
- 除了方向，也逐項驗證預測價格區間、情境目標、支撐與壓力。
- 不只看收盤漲跌，也要看盤中氛圍，例如開高走低、開低走高、放量下殺、縮量整理。
- 列出明顯準確與明顯不準確的股票清單。
- 對準確與不準案例保留原因標籤，並進一步建立有證據、反證、可能機制及反事實測試的因果候選。
- 支援因子歸零測試、移除測試與重新組合，避免模型只會越疊越肥。

## 不可變的事前預測快照

覆盤不得只從 `summary.json` 複製方向與少數摘要欄位。它必須讀取每檔原始預測 JSON，將下列內容原樣保存到 `prediction_snapshot.payload`：

- 方法版本、產生時間、預測模式、預測日、基準日及資訊截止時間。
- 原始方向、最終方向、方向分數、個股／市場／綜合風險分數。
- 資料完整度、缺漏資料、資料品質說明及回測狀態。
- `features` 的所有原始預測特徵。
- `view.scores` 的逐項分數、規則及當時數值。
- `view.scenarios` 的情境名稱、說明與目標區間。
- `view.levels` 的支撐、壓力、均線與波動上下緣。
- 其他原始預測 JSON 內的欄位；不得在覆盤時重新產生後冒充原值。

每份快照同時保存：

```text
source_file
source_sha256
expected_source_sha256
integrity_status
captured_at
payload
```

預測摘要建立時先把原檔雜湊寫入 `forecast_source_sha256`。覆盤時重新計算 `source_sha256`，並與 `expected_source_sha256` 比對：

- `verified`：與預測摘要建立時的雜湊相同。
- `mismatch`：內容已不同，覆盤必須警告且不得把它當作未變更的事前預測。
- `unavailable_preexisting_summary`：舊批次沒有預存雜湊，只能保留當下快照，不能聲稱完整性已驗證。

若未來需要修正預測格式，應建立新版檔案或另存更正紀錄，不得靜默改寫已覆盤的預測快照。

## 需要的實際行情資料

覆盤需要下一交易日的真實 OHLCV：

| 欄位 | 用途 |
|---|---|
| 前一交易日收盤價 | 計算開盤與收盤相對基準。 |
| 實際開盤價 | 判斷開高或開低。 |
| 實際最高價 | 判斷盤中上攻與震幅。 |
| 實際最低價 | 判斷盤中下殺與震幅。 |
| 實際收盤價 | 判斷最終方向。 |
| 實際成交量 | 判斷放量、縮量與氛圍強度。 |
| 5 日 / 20 日均量 | 作為成交量放大或萎縮基準。 |

以 `20260727` 預測批次為例，覆盤會比對：

```text
data_predictions/20260727/summary.json
data_fubon/fubon_20260727_sma.json
```

## 實際走勢標籤

第一版用規則產生每檔股票的 `actual_pattern_tags`：

| 標籤 | 初步判斷方式 |
|---|---|
| 開高走高 | 開盤高於前收，且收盤高於開盤。 |
| 開高走低 | 開盤高於前收，但收盤低於開盤。 |
| 開低走高 | 開盤低於前收，但收盤高於開盤。 |
| 開低走低 | 開盤低於前收，且收盤低於開盤。 |
| 放量上攻 | 成交量高於均量門檻，且收盤偏強。 |
| 放量下殺 | 成交量高於均量門檻，且收盤偏弱。 |
| 縮量整理 | 成交量低於均量門檻，且漲跌幅與震幅都不大。 |
| 長上影賣壓 | 盤中高點明顯高於收盤。 |
| 長下影承接 | 盤中低點明顯低於收盤。 |

實作時應保留原始數值，標籤只是方便 dashboard 與覆盤摘要閱讀。

## 實際氛圍分數

不要只用「收漲或收跌」判斷準不準。建議額外產生 `actual_mood_score`：

| 分數方向 | 可能來源 |
|---|---|
| 偏多加分 | 收盤上漲、開低走高、放量上攻、長下影承接。 |
| 偏空扣分 | 收盤下跌、開高走低、放量下殺、長上影賣壓。 |
| 中性 | 小漲小跌、縮量、低震幅。 |

可再轉成 `actual_mood_label`：

- 強多
- 偏多
- 中性
- 偏空
- 強空

## 準確度判斷

覆盤應產生兩種準確度：

| 欄位 | 說明 |
|---|---|
| `direction_accuracy` | 預測方向和實際收盤方向是否一致。 |
| `mood_accuracy` | 預測氛圍和實際盤中氛圍是否一致。 |

最後再合成 `prediction_match_label`：

- 明顯準確
- 大致準確
- 中性難判
- 大致不準
- 明顯不準

範例：

| 事前預測 | 實際走勢 | 判斷 |
|---|---|---|
| 偏多 | 開低走高、收漲、放量 | 明顯準確 |
| 偏多 | 開高走低、收黑、放量 | 明顯不準 |
| 偏空 | 開低走低、收跌、放量 | 明顯準確 |
| 偏空 | 開低走高、收紅、放量 | 明顯不準 |
| 中性 | 小幅震盪、縮量 | 大致準確 |

## 預測數字逐項驗證

方向正確不代表價格預測正確，因此每檔還要另外輸出 `forecast_target_evaluation`：

- 每個情境目標區間的數值上下界。
- 實際收盤是否落在該情境區間。
- 實際日內高低區間是否與預測區間重疊。
- 實際收盤落在區間外時，距離最近邊界的百分比。
- 每個支撐／壓力是否觸及。
- 支撐是否守住或收盤跌破。
- 壓力是否受阻或收盤突破。

這些判定必須和方向準確度分開。例如：

```text
方向：準確
收盤區間：不準
盤中區間：有重疊
支撐：觸及後跌破
```

第一版會解析既有 `view.scenarios[].target` 與 `view.levels[]`。後續預測格式應把中心價、收盤區間及盤中區間改成獨立數值欄位，避免依賴文字解析。

## 建議產出檔案

第一版可以產生三個檔案：

```text
data_predictions/YYYYMMDD/replay.json
data_predictions/YYYYMMDD/replay-summary.json
data_predictions/YYYYMMDD/replay-mistakes.json
```

### `replay.json`

逐檔股票覆盤資料：

- 完整原始預測快照、來源檔與 SHA-256。
- 原始預測方向、分數、風險、特徵、逐項計分、情境與價位。
- 實際 OHLCV。
- 實際開盤報酬、收盤報酬、盤中報酬、震幅、量比。
- 情境區間、支撐與壓力的逐項驗證。
- 實際走勢標籤。
- 準確度判斷。
- 原因標籤。
- 因果候選、證據狀態、反事實測試與限制。

### `replay-summary.json`

Dashboard 使用的摘要：

- 預測檔數。
- 已驗證檔數。
- 明顯準確數量。
- 明顯不準數量。
- 偏多命中率。
- 偏空命中率。
- 放量情境命中率。
- 開高走低誤判數。
- 開低走高漏判數。
- 產業命中率。
- 策略分類命中率。
- 概念股清單命中率。
- 預測時因子狀態的命中率差，例如籌碼同向、籌碼衝突、高風險環境及過熱。

### `replay-mistakes.json`

明顯不準案例集中分析：

- 股票清單。
- 原預測。
- 實際型態。
- 可能誤判原因。
- 周圍影響因素。
- 相關產業、策略標籤、概念股分類。
- 每個失敗候選原因的機制、證據狀態與下一個反事實測試。

## Dashboard 覆盤區塊

Dashboard 可以新增「事後覆盤」區塊：

- 如果 `replay-summary.json` 不存在，顯示「等待實際行情資料」。
- 如果存在，顯示覆盤 KPI。
- 列出「明顯準確」與「明顯不準」清單。
- 支援依產業、策略分類、概念股清單觀察命中率。

建議第一版先做：

- 明顯不準 Top 30。
- 誤判最集中的產業。
- 誤判最集中的概念股。
- 命中率最高的策略標籤。
- 命中率最低的策略標籤。

## 原因標籤

成功原因標籤範例：

- 技術轉強後續強。
- 放量配合方向。
- 產業同步偏多。
- 籌碼同步偏多。
- 大盤環境支持。
- 相對強勢有效。
- 低風險高完整度樣本命中。

失敗原因標籤範例：

- 開高出貨。
- 放量反殺。
- 量能不足。
- 產業拖累。
- 大盤或期貨反向。
- 高風險波動蓋過方向訊號。
- 籌碼與技術矛盾。
- 預測時資料缺漏。
- 前一日過熱導致隔日反轉。
- 個股新聞或事件影響。

## 從原因標籤走向因果分析

原因標籤只是索引，不等於因果結論。覆盤必須為每個候選原因輸出：

| 欄位 | 說明 |
|---|---|
| `factor_id` | 穩定的因子識別碼。 |
| `role` | `success_candidate`、`failure_candidate` 或 `unresolved`。 |
| `mechanism` | 該因素可能如何造成成功或失敗。 |
| `evidence_status` | 已觀察的直接路徑、待驗證假說或證據不足。 |
| `causal_confidence` | 對立即價格路徑與根本原因分開評級。 |
| `counterfactual_test` | 若拿掉或改變該因素，預測是否仍會相同的測試方法。 |

### 三層原因

1. **事前因素**：預測截止前已存在，例如籌碼與技術矛盾、過熱、高市場風險、資料缺漏。
2. **立即機制**：結果日實際發生的路徑，例如開高走低或開低走高。它能解釋預測如何失敗，但不一定是根本原因。
3. **外部觸發**：結果日新聞、法人、分點、產業或大盤衝擊。只有能證明發布時間及行情先後時，才可提高因果可信度。

結果日型態不得回填到事前預測模型，否則會造成未來資料洩漏。

### 第一階段：個案因果候選

每檔準確或不準案例先產生：

- 支持預測與反對預測的逐項分數。
- 移除單一分數後的 `score_without_factor` 與方向是否改變。
- 已觀察到的立即價格路徑。
- 一至多個候選成功／失敗機制。
- 支持證據、目前缺少的證據及下一個驗證方式。

單一股票單一交易日只能標記為 `causal_hypotheses_not_proven_causes`，不得宣稱已證明根本原因。

### 第二階段：同批次關聯篩選

在同一預測批次中，比較具有某項「事前因子狀態」與不具有該狀態的樣本：

```text
exposed_hit_rate
unexposed_hit_rate
hit_rate_difference
```

初始因子包括：

- `chip_aligned`
- `chip_conflicted`
- `high_risk_context`
- `high_data_completeness`
- `relative_strength_strong`
- `reversal_signal_present`
- `overextended_before_forecast`

同一天的股票受到共同市場衝擊，因此這只能標為 `exploratory_association`，不能直接當成因果效果。

### 第三階段：跨日反事實與消融

累積多個預測日後才進行：

- 移除單一因子並重算方向。
- 同市場環境、產業、方向強度與風險層級的配對比較。
- 市場日分組或固定效果，避免把單日大盤漲跌誤認為個股因果。
- 比較原模型與移除因子模型的命中率、平均報酬、區間覆蓋率。
- 使用 bootstrap 信賴區間；樣本不足時維持「證據不足」。

只有反事實重算在多個交易日持續改善或惡化，而且信賴區間不跨過中性基準時，才可把因果可信度由低提高。

## 因子實驗與歸零測試

覆盤系統不應只把更多因子加進模型。需要把因子拆成可開關的 registry：

```text
price_momentum
volume_expansion
sma_reclaim
macd_turn
kd_turn
chip_bias
relative_strength_7d
industry_strength
market_risk
news_confidence
data_completeness_penalty
concept_strength
```

每次覆盤後可以跑不同組合：

| 實驗 | 目的 |
|---|---|
| 全因子 | 目前完整模型表現。 |
| 歸零基準 | 不使用加權因子，只看最基礎方向。 |
| 只用技術 | 驗證技術面獨立效果。 |
| 只用籌碼 | 驗證籌碼面獨立效果。 |
| 只用市場風險 | 驗證大盤與新聞風險效果。 |
| 技術 + 量能 | 驗證價量組合。 |
| 技術 + 量能 + 產業 | 驗證產業同步是否改善。 |
| 全因子移除單一因子 | 做 ablation test，檢查某因子是否真的有用。 |

目標是找出：

- 哪些因子單獨有效。
- 哪些因子加入後改善明顯。
- 哪些因子移除後反而更好。
- 哪些因子只在特定環境有效。
- 哪些因子造成模型變肥但沒有提升。

建議後續產出：

```text
data_predictions/YYYYMMDD/factor-experiments.json
```

## 建議實作順序

1. 讀取 `summary.json`、每檔原始預測 JSON 與實際行情檔。
2. 凍結完整預測快照並保存 SHA-256。
3. 產生逐檔方向、實際型態、價格區間與關鍵價位驗證。
4. 產生原因標籤、逐項分數反事實與第一階段因果候選。
5. 產生 `replay.json`、`replay-summary.json` 與 `replay-mistakes.json`。
6. 在 dashboard 加入「事後覆盤」區塊。
7. 等 `2026-07-27` 真實行情抓到後，執行：

```bash
node scripts/generate_prediction_replay.js --date 20260727
```

或使用 npm script：

```bash
npm run replay:prediction -- --date 20260727
```

在實際行情尚未到位前，可用 `--dry-run` 搭配既有行情日測試流程是否正常，但這不代表真實覆盤結果：

```bash
node scripts/generate_prediction_replay.js --date 20260727 --actual-date 20260724 --dry-run
```

8. 第一版先人工核對明顯準確、明顯不準、區間命中與因果候選，不急著調整預測模型。
9. 累積多個交易日後，再做因子歸零、配對比較與重新組合。

## 20260727 第一版覆盤流程

當 `data_fubon/fubon_20260727_sma.json` 出現後：

1. 確認 `data_predictions/20260727/summary.json` 存在。
2. 執行覆盤腳本。
3. 產生 `replay.json`、`replay-summary.json`、`replay-mistakes.json`。
4. 驗證快照 SHA-256、預測價格數字及實際 OHLCV 沒有互相覆寫。
5. Dashboard 顯示覆盤區塊。
6. 人工檢查明顯準確、明顯不準、區間判定與候選因果是否合理。
7. 累積多日樣本後再進入因果與因子實驗。
